# Devotional Audio ("Listen") — Google Neural2 TTS + Devotional-of-the-Day

**Status:** design

## Problem

Devotional mode (`chatbot/devotional.py`, `DevotionalArtifact.tsx`) only
produces text — the user reads a 500-800 word devotional. There is no way
to listen to it. Separately, "Pick one for me" always resolves and
generates a fresh devotional per request (via the per-browser annual
rotation deck, `chatbot/devotional_rotation.py`), so a popular devotional
gets its ~500-800 words regenerated by the LLM, and would get its audio
regenerated, on every single request from every user.

## Spike findings (informs this design)

A throwaway script against Google Cloud Text-to-Speech (Neural2, see
`google-cloud-texttospeech`) established:

- **Voice/rate locked in:** `en-US-Neural2-C`, `speaking_rate=0.90`.
- **Background music locked in:** one fixed track, mixed under the
  narration via ffmpeg — `volume=0.168` gain, 2s fade-in, 4s fade-out,
  trimmed to the narration's exact length.
- **Latency:** ~4-9s to synthesize a full devotional (399 words → 4.06s in
  testing); ffmpeg mixing adds well under 1s. Acceptable for a single
  blocking request with a client-side loading state — no SSE needed for
  audio generation.
- **Cost:** ~$16 / 1M characters. A typical devotional (2,800-5,000 chars)
  costs a fraction of a cent per generation.
- **Real constraint:** `synthesizeSpeech` caps input at **5,000 characters
  per request**. Devotionals run 500-800 words (~2,800-5,000 chars per
  `DEVOTIONAL_PROMPT_TEMPLATE`), so the longer end of that range sits at or
  over the limit — generation must split on paragraph boundaries and
  concatenate, not assume one call always suffices.

## Approach

Two features, designed together because the second makes the first cheap
at scale:

1. **On-demand audio generation** for any devotional, with a full-screen
   synced-scroll "Listen" experience, cached by content hash so repeat
   listens never re-pay Google.
2. **Devotional-of-the-day**: the first "Pick one for me" generation each
   GMT+8 day becomes what every subsequent "Pick one for me" request
   returns that same day — so both the LLM devotional-text generation and
   (via the audio cache, transitively) the TTS generation happen at most
   once per day for that path, no matter how many users hit it.

Typed-reference and theme-based devotionals are **unaffected** by feature
2 — they always generate fresh, exactly as today. Feature 2 only changes
the rotation ("Pick one for me") branch of `stream_devotional`.

### Why these two features are designed together

Without devotional-of-the-day, "Pick one for me" text is different (or at
least re-generated) on almost every request, so the audio content-hash
cache would almost never hit for that path — defeating "generated once per
day." With it, the rotation path's text is stable for the whole calendar
day, so the *existing* hash-keyed audio cache naturally reuses the same
audio for everyone who listens to that day's devotional — no separate
audio-specific "once per day" logic is needed.

## Components

### `chatbot/devotional_audio.py` (new)

Wraps Google Cloud TTS + ffmpeg, mirroring how `ollama_client.py` isolates
the LLM provider behind the app's own function names.

- `synthesize_devotional_audio(text: str) -> bytes` (MP3 bytes):
  1. Split `text` into chunks on paragraph boundaries, each ≤ 5,000
     characters (mirrors `devotional.py`'s existing `_MAX_RANGE_SPAN`-style
     defensive clamping for long input).
  2. Call `texttospeech.TextToSpeechClient().synthesize_speech` per chunk
     — voice `en-US-Neural2-C`, `speaking_rate=0.90`, MP3 encoding.
  3. Concatenate the chunk MP3s via ffmpeg (`concat` demuxer).
  4. Mix the concatenated narration with the bundled background track
     (`chatbot/data/devotional_stillness.mp3`) using the locked ffmpeg
     filter: `volume=0.168`, `afade` in 2s / out 4s, `amix duration=first`
     (narration length wins).
  5. Return the final MP3 bytes.
- Raises a `DevotionalAudioError` on any TTS or ffmpeg failure; callers
  turn that into a clean client-facing error, never a 500 with a
  traceback.

### Audio cache (filesystem, new `AUDIO_CACHE/` dir)

Same pattern as `CACHED_PAGES/` (Flask's `flask_caching` filesystem
cache) — a writable directory, mounted as a Docker named volume for the
`chatbot` service.

- Cache key: SHA-256 of `(text, voice_name, speaking_rate, music_track_id,
  music_gain)` — hex digest as the filename, e.g.
  `AUDIO_CACHE/<hash>.mp3`. Including the non-text parameters means
  changing the locked voice/rate/music settings later auto-invalidates old
  entries rather than serving stale audio under new "current" settings.
- No active eviction. At roughly one new unique devotional per day (from
  feature 2) plus occasional typed/theme listens, growth is on the order
  of megabytes per day — not worth building retention logic for v1.

### `POST /api/devotional/audio` (new endpoint, `chatbot/api.py`)

Request: `{reference: str, text: str}` (the client already has both from
the completed devotional artifact). Response: `{audio_url: str}`.

1. Compute the cache key from `text` + the fixed voice/rate/music
   constants.
2. Cache hit → return its URL immediately, no TTS/ffmpeg call.
3. Cache miss → call `synthesize_devotional_audio`, write the result to
   `AUDIO_CACHE/<hash>.mp3`, return its URL.
4. On `DevotionalAudioError` → `502` with a plain error message; the
   frontend shows an inline failure state. The existing text-based
   devotional flow is entirely unaffected — this is a separate, later,
   optional call the user only reaches by clicking "Listen".

Synchronous (blocking), not SSE — spike latency (single-digit seconds) is
fine for a request with a client-side spinner.

### Static serving

FastAPI mounts `AUDIO_CACHE/` as static files (e.g.
`/devotional-audio/<hash>.mp3`), the same idea as Flask's `/LC_/` mount for
manuscript images.

### Devotional-of-the-day (`chatbot/devotional_of_day.py`, new)

A tiny SQLite-backed store, following the `shares.db` / `feedback.db`
convention (own file, own env var `DEVOTIONAL_OF_DAY_DB_URL`, default
`sqlite:///devotional-of-day.db`).

```sql
CREATE TABLE daily_devotional (
    date_gmt8   TEXT PRIMARY KEY,   -- 'YYYY-MM-DD' in fixed UTC+8
    reference   TEXT NOT NULL,
    translations_json TEXT NOT NULL,
    text        TEXT NOT NULL,
    created_at  TEXT NOT NULL
);
```

- **Day boundary:** `date_gmt8 = (datetime.now(timezone.utc) +
  timedelta(hours=8)).date().isoformat()`. A fixed offset, not a named
  timezone — GMT+8 (e.g. Singapore, Shanghai, Kuala Lumpur) has no DST, so
  this is simple and correct with no `zoneinfo` dependency.
- **Serve hook**, in `stream_devotional`'s rotation branch only (`source`
  implies "Pick one for me", i.e. the existing `rotation is not None`,
  no-theme case): before calling `_resolve_rotation_seed_verse` or the
  LLM, `SELECT * FROM daily_devotional WHERE date_gmt8 = :today`.
  - Hit → yield `{"type": "done", "text", "reference", "translations",
    "from_daily_cache": True}` directly. No verse resolution, no LLM call.
  - Miss → proceed exactly as today's rotation flow
    (`_resolve_rotation_seed_verse` → `stream_devotional_completion`).
- **Capture hook**, same branch, only on a miss that finishes generating
  successfully: `INSERT OR IGNORE INTO daily_devotional (...) VALUES
  (:today, ...)`. If another concurrent request already inserted today's
  row, this is a no-op — the affected-rows count is 0, and *this*
  request's own caller still gets its own freshly generated result back
  unchanged (it just doesn't become canonical). This is the only
  concurrency handling needed: rare, low-cost, no locking.
- Typed-reference and theme paths in `stream_devotional` never read or
  write this table — untouched, always fresh, exactly as today.
- **Expiry:** none, actively. Every read filters on `date_gmt8 = :today`,
  so once GMT+8 rolls over the previous day's row is simply never matched
  again — functionally discarded without a cron job. Rows are tiny
  (a devotional's text) and accumulate harmlessly; not worth building
  retention cleanup for v1.
- **Audio reuse falls out for free:** because the rotation path's text is
  now stable for the whole GMT+8 day, the audio content-hash cache
  (above) naturally produces one cache entry per day for this path — the
  first "Listen" click generates it, every later listener (any user) hits
  the cache.

### API response field (`chatbot/api.py`)

The devotional `final` SSE event's `data` gains `from_daily_cache: bool`
(false for typed reference / theme, and for a rotation miss; true for a
rotation hit).

### Frontend: `useDevotionalRotationStore`

Its cursor-advance call (fired after a "Pick one for me" response) is
gated on `from_daily_cache`: `false` → advance the local `(seed, cursor)`
as today; `true` → do not advance — the user didn't consume their own
deck's next card, so it stays available for the next day they generate
first or the shared-of-the-day behavior doesn't apply.

### Frontend: `DevotionalListenOverlay.tsx` (new)

A full-viewport overlay, portaled to `document.body`
(`position: fixed; inset: 0`, high z-index — covers the entire app,
including header/nav).

- **Trigger:** a "Listen" button added next to the existing copy button in
  `DevotionalArtifact.tsx`. Click opens the overlay immediately (gradient
  background + devotional text visible, not yet scrolling) and fires
  `POST /api/devotional/audio` (instant if cached).
- **Loading state:** shown in the overlay while the audio request is in
  flight.
- **Scroll sync:** once the `<audio>` element's `loadedmetadata` gives its
  duration, scroll position is driven every animation frame by
  `audio.currentTime / audio.duration` — not an independent timer. Pause
  is simply "`currentTime` stops advancing"; resume picks up exactly where
  it left off, and stays correct even through a buffering stall.
- **Controls:** a play/pause toggle (`audio.pause()` / `audio.play()`;
  scroll follows automatically) and a "Done" button. Done pauses the
  audio, unmounts the overlay, and returns to the exact prior UI — the
  normal `DevotionalArtifact` panel, Listen button ready to reopen.
- **Background:** a slow CSS-animated gradient using the app's existing
  theme tokens (light/dark mode both covered, no new image assets).
- **Failure state:** if the audio request fails, show an inline error with
  only "Done" active — falls back to the normal text view, never traps
  the user in the overlay.

## Data flow

**Typed reference / theme (unchanged from today, plus optional audio):**
user types → `stream_devotional` resolves + generates as today →
`DevotionalArtifact` renders text → user optionally clicks Listen →
`POST /api/devotional/audio` (cache miss the first time anyone requests
audio for that exact text, hit thereafter) → `DevotionalListenOverlay`
plays.

**"Pick one for me," first request of the GMT+8 day:** rotation resolves +
LLM generates as today → capture hook persists it as `daily_devotional` →
delivered normally, `from_daily_cache: false` → cursor advances.

**"Pick one for me," later requests the same day:** serve hook returns the
persisted text instantly, `from_daily_cache: true`, no LLM call → cursor
does not advance → if the user clicks Listen, the audio cache almost
certainly already has this exact text's audio (from an earlier listener
that day), so it's an instant serve too.

## Deployment

- `requirements.txt`: add `google-cloud-texttospeech`.
- `Dockerfile.chatbot`: install `ffmpeg` (`apt-get install -y ffmpeg`) —
  not present in `python:3.13-slim`.
- `chatbot/data/devotional_stillness.mp3`: the fixed background track,
  committed to the repo (static, reused asset — not user data).
- `docker-compose.yml` (`chatbot` service):
  - New writable named volume for `AUDIO_CACHE/`.
  - New writable named volume / mount for `devotional-of-day.db`
    (`DEVOTIONAL_OF_DAY_DB_URL`, same pattern as `SHARE_DB_URL`).
  - Mount the Google Cloud service-account JSON read-only; set
    `GOOGLE_APPLICATION_CREDENTIALS` to its in-container path. The key
    itself is never committed — path only, via `.env`, matching every
    other credential in this repo.
  - `.env.example` gains a documented (blank) entry for the credentials
    path and any TTS-related env vars.

## Error handling

- TTS failure, ffmpeg failure, or (defensively) an empty devotional text
  reaching the audio endpoint all return a clean error response — never a
  raw exception. The core text-based devotional flow is completely
  unaffected by any audio failure, since audio is a strictly later,
  optional, separate request.
- A `daily_devotional` read/write failure (e.g. the sqlite file is
  temporarily locked) should fail open to "generate fresh," not block
  "Pick one for me" entirely — a request that can't check or write the
  daily cache still needs to succeed as an ordinary generation.

## Testing

- Unit tests for `synthesize_devotional_audio`'s paragraph-boundary
  chunking at the 5,000-character limit, with the Google TTS client and
  ffmpeg calls mocked (consistent with how `test_devotional_stream.py`
  mocks the LLM layer) — verifying chunk boundaries never split mid-word
  and the concatenation order is preserved.
- Unit tests for the audio cache key: same `(text, voice, rate, track,
  gain)` → same hash; any one differing → different hash.
- Unit tests for `devotional_of_day`: a miss followed by a hit within the
  same `date_gmt8` returns the persisted text without a second LLM call;
  a concurrent-insert race leaves exactly one canonical row and does not
  raise; a request on a later `date_gmt8` misses and generates fresh.
- Unit test confirming typed-reference and theme paths never touch
  `daily_devotional` (no read, no write) — guards against feature 2
  accidentally leaking into those paths.
- Frontend test for `useDevotionalRotationStore`: cursor does not advance
  when `from_daily_cache: true`, does advance when `false` (existing
  behavior preserved).

## Out of scope (v1)

- A library/rotation of multiple background tracks — one fixed track only.
- Any voice/rate/music setting exposed as a user-facing control — the
  spike-validated settings are hardcoded constants.
- Active eviction/retention jobs for either the audio cache or
  `daily_devotional` rows — both rely on natural date-based
  irrelevance / low growth rate instead.
- Per-user accounts or server-side listening history — sessions remain
  browser-local, exactly as the rest of the app.
