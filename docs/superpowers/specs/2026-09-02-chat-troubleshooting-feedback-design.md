# Chat Troubleshooting & Feedback Design Spec

**Date:** 2026-09-02
**Status:** Approved for planning

## Purpose

Give users a way to report problems with a chat session, and give the admin
enough captured detail to diagnose the cause. A "Report an issue" control on
every chat session submits the whole conversation — plus a **turn-by-turn
trace** of what the backend did for each assistant turn (routing decisions,
tool calls, LLM calls, timings, token counts) — to a backend database. An
admin-only view renders each submission as a trajectory inspector modelled on
`Design2.png`: an Input/Model/Tools timeline bar, an expandable turn→step
tree, and a per-step detail panel (Source, Status, Tokens, Preview, Request
Timing).

## Scope

**In scope:**

- A per-request **trace recorder** in the chatbot FastAPI service that
  records each routing branch, tool call, and LLM call for a chat turn, and
  returns a structured `trace` object in the chat response.
- Trace coverage for **all chat-turn paths**: non-streaming `POST /chat`,
  streaming `POST /chat/stream` (SSE), and mode primers
  (`build_mode_primer`).
- Frontend changes to store each turn's `trace` on its assistant
  `SessionMessage` in the existing `localStorage`-backed session store.
- A `ReportIssueDialog` in the React shell (`ChatPane` header) and in the
  embeddable `BibleChatWidget`, which bundles the active session (messages +
  per-message traces + client metadata + a user description) and uploads it.
- A new writable SQLite database (`feedback.db`) and Flask endpoints:
  `POST /api/feedback` (public ingest), and Basic-auth-protected
  `GET /api/admin/feedback`, `GET /api/admin/feedback/<id>`,
  `PATCH /api/admin/feedback/<id>`.
- A new React `/admin` route: a submissions list and a `Design2.png`-style
  trajectory detail view, with editable triage `status` and `admin_notes`.
- HTTP Basic auth (env-var credentials) as the sole gate on all admin
  surfaces.
- Deployment wiring: a Docker volume for `feedback.db`, new env vars,
  `.env.example` / `DEPLOYMENT.md` updates. No nginx change.

**Out of scope:**

- Tracing the direct artifact/tool endpoints (`/verse`, `/passage`,
  `/study`, `/strongs`, `/book_context`, `/parables`, `/study-wikis`) —
  those are not conversation turns.
- User accounts, multi-admin roles, or session-cookie login. Basic auth
  with a single credential pair is the whole auth model.
- Editing, re-running, or replaying a captured trace.
- Analytics or dashboards aggregated across reports; CSV/JSON export.
- Automatic retention / pruning of `feedback.db` (single admin, low volume;
  revisit if it grows).
- Server-side sync or persistence of chat sessions for non-reporters — the
  chatbot stays stateless and only *reports* reach a database.
- Changing the existing thumbs-up/down message feedback (local-only state in
  `ChatPane`); it is left as-is.

## Architecture Overview

| Component | Location | Responsibility |
|---|---|---|
| Trace recorder | `chatbot/` (FastAPI) | Record routing/tool/LLM steps per turn; attach `trace` to the response |
| Report dialog + client metadata | `frontend/src/` (React) | Trigger on every session; assemble and POST the report |
| Session store change | `frontend/src/store/useSessionsStore.ts` | Persist `trace` on each assistant `SessionMessage` |
| Feedback store + APIs | `myproject.py` (Flask) | `feedback.db`; ingest + Basic-auth admin read/patch |
| Admin trajectory viewer | `frontend/src/` (React, `/admin`) | List + `Design2.png`-style detail inspector |

**Guiding principle:** the chatbot service remains stateless. The trace is
computed in-request and returned to the client; it lives in the browser
session alongside the messages; it reaches a database only when the user
files a report.

### Request flow (unchanged paths, new trace output)

```
Browser (ChatPane / BibleChatWidget)
  → nginx  /api/bible-chat/*  → flask-api  → chatbot FastAPI
       route_deterministic → tools.py (HTTP to flask-api / external)
       route_claude        → ollama_client.py (Ollama | NVIDIA NIM)
       build_mode_primer
  ← ChatResponse + trace  (non-stream)
  ← SSE … then a terminal `event: trace` frame  (stream)

Browser ("Report an issue")
  → nginx  POST /api/feedback  → flask-api  → INSERT into feedback.db

Admin (React /admin)
  → nginx  GET/PATCH /api/admin/feedback*  → flask-api (Basic auth) → feedback.db
```

## Data Model

### Trace object (wire + stored on the message)

Returned as an optional `trace` field on the chat response; stored verbatim
on the assistant `SessionMessage`. Field names are the wire contract shared
by chatbot, frontend store, and admin viewer.

```
Trace {
  turnId: string                       // uuid, generated by the recorder
  requestPath: "/chat" | "/chat/stream" | "primer"
  startedAt: number                    // epoch ms
  endedAt: number
  durationMs: number
  input: {
    message: string
    mode: string | null
    modeParams: object | null
    historyLength: number
    pageContext: string | null
  }
  steps: Step[]
  outcome: {
    type: string                       // ChatResponse.type ("verse" | "chat" | "error" | ...)
    route: string | null               // existing human-readable route string
    error: string | null
  }
  totals: {
    toolCalls: number
    llmCalls: number
    llmTokens: number | null           // sum of step token totals when any are known
    durationMs: number
  }
}

Step {
  index: number                        // 0-based, execution order
  kind: "routing" | "context" | "tool" | "llm"
  label: string                        // "route_deterministic" | "fetch_scripture_study"
                                       //   | "Ollama (deepseek-v4-pro:cloud)"
  startedAt: number
  endedAt: number
  durationMs: number
  status: "completed" | "error" | "skipped"
  request: object | null               // tool: { args, url? };  llm: { system, messages, params }
  response: object | null              // tool: { preview, bytesTotal };  llm: { content, bytesTotal }
  tokens: { prompt: number, completion: number, total: number } | null
  error: string | null
}
```

- **Step kinds → Design2.png bands.** `context` + `routing` feed the *Input*
  band; `llm` feeds *Model*; `tool` feeds *Tools*. The viewer lays each step
  on the timeline by `startedAt`/`durationMs` relative to the turn window.
- **`routing` steps** record which deterministic branch matched (e.g.
  `"deterministic: study keyword"`), or `"fell through to LLM"`.
- **`context` steps** record grounding assembly (e.g.
  `_fetch_research_data`, wiki retrieval) with a preview of what was
  attached.
- **Truncation.** Any `request`/`response` string value is truncated to a
  16 KB preview; the untruncated byte length is kept as `bytesTotal`.
  Mirrors the viewer's "Preview" affordance — full bodies are never stored.
- **Redaction (hard requirement).** Before a `request` is stored the
  recorder removes `Authorization` headers and replaces any substring equal
  to a `*_API_KEY` / `*_TOKEN` environment value with `"[redacted]"`.

### `feedback.db` — table `reports`

New SQLite file at the repo root (`feedback.db`), opened read-write via the
`dataset` library (already a dependency). Gitignored. Docker volume-mounted
(see Deployment). Single denormalized table — the trajectory detail lives
entirely inside `session_json`, so there are no joins.

| Column | Type | Notes |
|---|---|---|
| `id` | TEXT (uuid4) | Primary key |
| `created_at` | TEXT (ISO 8601 UTC) | Server-set |
| `client_id` | TEXT | Persistent random id from the browser (localStorage) |
| `email` | TEXT NULL | Optional, user-entered |
| `category` | TEXT | One of: `wrong_answer`, `error`, `slow`, `ui`, `other` |
| `description` | TEXT | Required, user-entered; server caps at 8 KB |
| `session_json` | TEXT | Full session: mode, modeParams, title, messages[], each assistant message's `trace` |
| `session_mode` | TEXT | Denormalized for list filtering |
| `session_title` | TEXT | Denormalized for the list |
| `message_count` | INTEGER | Denormalized |
| `app_version` | TEXT | `VITE_APP_VERSION` at build time |
| `user_agent` | TEXT | `navigator.userAgent` |
| `viewport` | TEXT | `"{w}x{h}"` |
| `page_url` | TEXT | `location.href` at submit |
| `status` | TEXT | `new` \| `triaged` \| `resolved`; default `new`; admin-editable |
| `admin_notes` | TEXT NULL | Admin-editable |

The table is created on first write if absent (`dataset` auto-creates
columns from the first insert; an explicit `CREATE TABLE` guard in a small
`feedback_store.py` keeps the schema stable and indexes `created_at`,
`status`).

## Backend: Trace Capture (chatbot service)

### Recorder plumbing

- New module `chatbot/trace.py`:
  - `TraceRecorder` — holds `turnId`, `input`, an ordered `steps` list,
    start time, and helper methods `add_routing(label, status=...)`,
    `tool_step(label, request)` (context manager: times the body, captures
    result preview + `bytesTotal`, records `error`/`status`),
    `llm_step(label, request)` (same, plus `tokens`), `context_step(...)`.
  - `current_recorder: ContextVar[TraceRecorder | None]` — set at request
    entry, read by the wrappers. `contextvars` propagates across `await` and
    is copied into `asyncio.gather` children, so concurrent tool fetches
    (`_fetch_research_data`, `hydrate`) each record correctly.
  - `finalize(outcome) -> dict` — computes `endedAt`, `durationMs`,
    `totals`, returns the `Trace` dict.
  - `redact(obj) -> obj` — applied inside every `*_step` before storing
    `request`.

### Hook points

- `chatbot/api.py`
  - `post_chat`: create a recorder, set the ContextVar, run the existing
    flow, call `finalize(...)`, attach `trace` to the `ChatResponse`. The
    broad `except Exception` handler also finalizes (status `error`, the
    exception recorded on the outcome) so a crashed turn still produces a
    trace.
  - `post_chat_stream` / `_stream_chat_response`: same recorder; after the
    existing `done` event, emit one more SSE frame
    `data: {"type":"trace", ...}` carrying `finalize(...)`.
- `chatbot/router.py`
  - `route_deterministic`: an `add_routing(...)` call at each early return
    naming the branch (`"random verse keyword"`, `"gematria value match"`,
    `"strongs number match"`, `"study keyword"`, `"quote keyword"`,
    `"book context"`, `"default verse lookup"`, …), and one
    `add_routing("fell through to LLM", status="completed")` at the final
    `return None`.
  - `route_claude` / `_enhance_with_cited_verse`: `context_step` for the
    cited-verse enrichment fetches.
  - `build_mode_primer`: `add_routing("mode primer: <mode>")` plus
    `tool_step` around its `fetch_*` calls.
  - `wiki_qa.answer`: `context_step` around wiki retrieval.
- `chatbot/tools.py`
  - Wrap the body of each public async tool (`fetch_verse_translations`,
    `fetch_scripture_study`, `fetch_strongs`, `search_gematria`,
    `search_english`, `list_passage_verses`, `random_verse`) in
    `recorder.tool_step(name, {"args": ...})` when a recorder is set;
    no-op otherwise. Result preview = `json.dumps(result)[:16384]`.
- `chatbot/ollama_client.py`
  - `call_ollama_with_context` and `stream_chat_with_ollama`: wrap the HTTP
    call in `recorder.llm_step(active_model_label(), {"system": system_prompt,
    "messages": messages, "params": {...}})`. `response` = the assembled
    content. `tokens`: Ollama → `prompt_eval_count` / `eval_count` from the
    final JSON object; NVIDIA → `usage.prompt_tokens` /
    `usage.completion_tokens`. `null` when the provider doesn't report them.

### Schema change

`chatbot/schemas.py`: add `trace: Optional[Dict[str, Any]] = None` to
`ChatResponse`. No other schema changes; `ChatRequest` is untouched (no
`conversation_id` plumbing — the trace is self-contained per turn).

### Size & safety

- A turn's trace is bounded by per-step 16 KB previews; a whole session's
  worth (dozens of turns) stays well under nginx's 12 MB body cap.
- The recorder never raises into the request path: every helper swallows its
  own errors and records `status:"error"` instead.

## Backend: Ingest & Admin API (Flask, `myproject.py`)

New module `feedback_store.py` (DB open/create/query helpers) plus routes in
`myproject.py`.

- `POST /api/feedback` — **public, no auth.**
  - Rejects bodies larger than 5 MB (`413`) — checked before JSON parse.
  - Validates: `category` in the allowed set, `description` non-empty
    (trimmed, capped 8 KB), `session_json` present and parses as an object
    with a `messages` array. `email` optional, shape-checked if present.
  - Derives `session_mode`, `session_title`, `message_count` server-side
    from the parsed session (not trusted from separate fields).
  - Inserts one row; returns `201 {"id": "<uuid>"}`.
  - Best-effort per-IP rate limit (in-process token bucket, e.g. 5 / min) →
    `429` when exceeded. No external dependency.
- `GET /api/admin/feedback` — **Basic auth.** Query params `status`,
  `category`, `limit` (default 50, max 200), `offset`. Returns
  `{ total, items: [{ id, created_at, category, status, session_mode,
  session_title, message_count, has_email }] }`. Never returns
  `session_json` in the list.
- `GET /api/admin/feedback/<id>` — **Basic auth.** Full row including parsed
  `session_json`. `404` if unknown.
- `PATCH /api/admin/feedback/<id>` — **Basic auth.** Accepts `status`
  (allowed set) and/or `admin_notes` (capped 16 KB). Returns the updated
  row. `404` if unknown.

### Auth

- `require_admin` decorator: reads `ADMIN_USER` / `ADMIN_PASSWORD` from the
  environment. Missing/blank config → `503` (admin disabled) rather than an
  open door. Compares both fields with `hmac.compare_digest`. On failure:
  `401` with `WWW-Authenticate: Basic realm="admin"`.
- Applied to the three `/api/admin/*` routes. All under `/api/` so nginx
  already proxies them to Flask unchanged.

## Frontend: Reporting

### Client id

- New `frontend/src/lib/clientId.ts`: `getClientId()` reads
  `localStorage["bible-explorer-client-id"]`, generating and storing a
  `crypto.randomUUID()` on first use. Wrapped in try/catch (private-mode
  storage failures fall back to an in-memory id for the tab).

### `ReportIssueDialog`

- New `frontend/src/components/shell/ReportIssueDialog.tsx`. Modal:
  - `category` `<select>`: Wrong answer / Error or crash / Too slow / UI
    problem / Other (→ `wrong_answer|error|slow|ui|other`).
  - `description` `<textarea>` — required, live-validated, 8 KB max.
  - `email` `<input type="email">` — optional.
  - Submit / Cancel. Submitting disables the form; success shows a brief
    confirmation then closes; failure shows an inline error and keeps the
    entered text.
- `frontend/src/lib/feedbackApi.ts`: `submitReport(session, form)` builds

  ```
  {
    category, description, email?,
    client_id, app_version, user_agent, viewport, page_url,
    session_json: {
      id, mode, modeParams, title,
      messages: session.messages   // assistant messages already carry `trace`
    }
  }
  ```

  and `POST`s it to `/api/feedback` via the existing `parseJsonResponse`
  guard.

### Trigger placement

- `ChatPane` header: a small "Report an issue" button beside the mode chip.
  Opens the dialog for the active session.
- `BibleChatWidget`: an equivalent affordance in its header/menu, wired to
  the same dialog + `submitReport`, using whatever session/message state the
  widget holds. This is what makes the control present on *every* chat
  session, embedded or in-shell.

### Storing the trace

- `frontend/src/types/session.ts`: add `trace?: Trace` to `SessionMessage`;
  add a `Trace` / `TraceStep` type module (`frontend/src/types/trace.ts`)
  matching the wire contract.
- `frontend/src/lib/chatApi.ts`: `ChatApiResponse` gains `trace?`. `postChat`
  passes it through.
- `frontend/src/components/shell/ChatPane.tsx`: `sendMessage`, `regenerate`,
  `markDayComplete`, and the choice-resolution paths store
  `response.trace` on the appended/updated assistant message.
- Streaming (`BibleChatWidget` / `chatApi` stream reader): on the terminal
  `type:"trace"` SSE event, attach it to the just-completed assistant
  message.
- `useSessionsStore`: bump `version` to `2`; the `merge`/`migrate`
  sanitizers already drop unknown/old shapes safely, and `trace` is
  optional so v1 sessions load unchanged.

## Frontend: Admin Trajectory Viewer

- New route, reached at `/admin` (a lightweight client-side check in
  `App.tsx` / a small router: if `location.pathname` starts with `/admin`,
  render `<AdminApp>` instead of the normal shell). The `/api/admin/*` calls
  carry the browser's Basic-auth credentials; a `401`/`503` renders a
  "sign in as admin" / "admin disabled" message instead of the data.
- `frontend/src/components/admin/AdminListView.tsx`: table of reports
  (created_at, category, status, mode, message_count, email indicator),
  `status`/`category` filters, pagination, row → detail.
- `frontend/src/components/admin/AdminReportView.tsx` — the `Design2.png`
  layout:
  - **Transcript column**: the conversation (user + assistant turns) from
    `session_json.messages`.
  - **Trajectory panel** (per assistant turn that has a `trace`):
    - **Timeline bar**: Input / Model / Tools rows; each `step` drawn as a
      segment positioned by `startedAt`/`durationMs` within the turn window.
      A Duration / Turns / Calls toggle changes the segment grouping, as in
      the mockup.
    - **Step tree**: ordered rows — `SYSTEM` (llm `request.system`),
      `USER` (turn input), `CONTEXT` (context steps), one row per `tool`
      step, `ASSISTANT` (final answer). Expand/collapse.
  - **Detail drawer** (on step select): Source (`step.label` / `outcome.route`),
    Status, Tokens (`step.tokens`), Preview (`request` / `response`
    pretty-printed, with a "truncated — N bytes total" note when
    `bytesTotal` exceeds the preview), Request Timing (`durationMs`,
    absolute start/end).
  - **Triage controls**: `status` `<select>` and `admin_notes` `<textarea>`,
    saved via `PATCH /api/admin/feedback/<id>`; optimistic update with
    error rollback.
- Styling reuses the existing Tailwind theme tokens
  (`--color-theme-*`, `--color-surface*`). The admin components are only
  imported by the `/admin` entry so they add nothing to the normal user
  bundle path that matters at this scale (code-split via dynamic import).

## Error Handling

- **Recorder failure** never breaks a turn — helpers catch internally and
  record `status:"error"`; a completely absent/failed recorder just means
  `trace` is `null` and the chat response is unchanged.
- **`trace` missing on a message** (old session, streaming event lost,
  backend older than frontend): the report still submits; the admin viewer
  shows "no trace captured for this turn".
- **Ingest validation failure**: `400` with a machine-readable `error` code;
  the dialog surfaces a generic "couldn't submit" message and keeps the
  user's text.
- **Oversize report**: `413`; dialog message suggests the conversation is
  too large to attach (rare — would need a very long session).
- **Admin not configured** (`ADMIN_USER`/`ADMIN_PASSWORD` unset): admin
  routes return `503`; the admin UI shows "admin access is not configured on
  this server".
- **`feedback.db` unwritable** (bad volume mount / permissions): ingest
  returns `500` with a logged error; no user data is lost silently — the
  dialog reports failure.

## Deployment

- **`feedback.db` persistence.** Add a named volume in `docker-compose.yml`
  mounted into the `flask-api` service at the repo path where
  `feedback_store.py` opens the DB (e.g. `/app/feedback.db`). Document in
  `DEPLOYMENT.md`. The `dataset`/SQLite write path must be on the volume,
  not the image layer.
- **Env vars** (add to `.env.example` with comments):
  - `ADMIN_USER`, `ADMIN_PASSWORD` — flask-api; unset ⇒ admin disabled.
  - `VITE_APP_VERSION` — frontend build-time; surfaced in reports.
- **nginx:** no change. Ingest (`/api/feedback`) and admin
  (`/api/admin/*`) both fall under the existing `location /api/` proxy; the
  `/admin` page is served by the SPA `try_files` fallback.
- **`.gitignore`:** add `feedback.db`, `feedback.db-shm`, `feedback.db-wal`.

## Testing

**Backend — chatbot:**

- `TraceRecorder` unit tests: step ordering and indices; `durationMs`
  monotonic; `totals` aggregation; redaction of `Authorization` and
  `*_API_KEY` values; 16 KB preview truncation with correct `bytesTotal`.
- `POST /chat` integration: a deterministic route (e.g. "quote John 3:16")
  produces a `trace` with a `routing` step and a `tool` step and no `llm`
  step; a mocked-LLM fallback produces an `llm` step with `tokens`
  populated; a forced exception still returns a finalized `trace` with
  `outcome.error`.
- `POST /chat/stream`: the terminal `type:"trace"` SSE frame is emitted
  after `done` and parses to the same shape.

**Backend — Flask:**

- `POST /api/feedback`: happy path returns `201` + `id` and a row is
  present; oversize body → `413`; bad `category` / empty `description` /
  malformed `session_json` → `400`; denormalized fields are derived
  server-side, not copied from the request.
- Admin auth: no credentials → `401` + `WWW-Authenticate`; wrong
  credentials → `401`; correct → `200`; unset env → `503`.
- `GET /api/admin/feedback` never includes `session_json`; filters and
  pagination behave; `GET .../<id>` returns it; `PATCH` updates `status` /
  `admin_notes` and rejects an out-of-set `status`.

**Frontend:**

- `clientId`: generates once, persists, survives a reload (mocked
  `localStorage`); in-memory fallback when storage throws.
- `ReportIssueDialog`: description required; category maps to the wire enum;
  submit assembles the documented payload; failure keeps entered text.
- `chatApi` / stream reader: `trace` passed through on `postChat`; the
  terminal `trace` SSE event attaches to the last assistant message.
- `useSessionsStore`: a v1 persisted blob (no `trace`) loads under v2
  unchanged; a message with a `trace` round-trips through persist/hydrate.
- Admin `AdminReportView`: renders timeline bands and the step tree from a
  fixture trace; the detail drawer shows tokens/timing/preview; a
  truncated step shows the "N bytes total" note; `PATCH` failure rolls the
  triage control back.

## Rejected Approaches

- **Always-on server-side trace store** (frontend sends a stable
  `conversation_id`; backend writes every turn's trace for all traffic).
  Rejected: makes the chatbot stateful, stores data for every visitor
  rather than only reporters, and needs a retention story. The in-response
  trace gives the same fidelity for the turns that actually get reported.
- **Lightweight reconstruction** from the existing one-line `route` string
  plus client-measured latency. Rejected: no per-step timing, token counts,
  or prompts — not enough to reproduce `Design2.png` or to diagnose a bad
  answer.
- **Server-rendered Flask admin page.** Rejected: the trajectory inspector
  is interactive (timeline, expandable tree, detail drawer); the React
  shell already has the styling and component patterns for it.
- **Secret-token / full-login auth.** Basic auth via env vars is revocable
  by redeploy, needs no user table, and fits the current single-admin
  deployment.
